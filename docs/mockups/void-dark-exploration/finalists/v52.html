The quiet art of naming things well

March 2, 2026 8 min read

Good names don't describe what something is. They shape how you think about it. The best code reads like well-edited prose, not because it's clever, but because every name carries exactly the weight it should.

I spent twenty minutes last week renaming a variable. Not because the old name was wrong, but because it was imprecise. It said data when it meant userPreferences. That kind of vagueness compounds. Three months from now, someone reads that code and has to rebuild context that should have been free.

This isn't pedantry. It's the cheapest form of documentation you'll ever write. A well-named function is a promise. A well-named module is a boundary. Get them right and your architecture explains itself.

Names as cognitive shortcuts

When you read processItems(), you know nothing. When you read archiveExpiredListings(), you know everything. The second name does work that would otherwise require a comment, a Slack message, or ten minutes of reading implementation details.

There are only two hard things in Computer Science: cache invalidation and naming things.

Phil Karlton said that, and it's become a cliche because it's true. But I'd add a corollary: naming things is hard because it requires you to actually understand what you're building. The struggle to name something is often the struggle to define it.

The spectrum of specificity

Names exist on a spectrum. Too vague and they carry no meaning. Too specific and they become brittle, breaking every time the implementation shifts. The sweet spot is a name that captures intent without over-committing to mechanics.

// Too vague
const handle = (x) => { ... }

// Too specific
const parseJsonAndExtractUserEmailFromResponse = (res) => { ... }

// Just right
const extractUserEmail = (response) => { ... }

The third version tells you what it does without telling you how. If you later switch from JSON to protobuf, the name still holds. That resilience matters more than you think.

Naming as design pressure

Here's something I've noticed over the years: when a name feels awkward, the abstraction is usually wrong. If you can't name a function simply, it's probably doing too much. If a module name requires a conjunction, it probably needs to be split.

  • If the name needs "and," the function does too much
  • If the name needs "or," the type is too broad
  • If the name needs a number suffix, the architecture needs rethinking
  • If the name is generic, the concept hasn't been found yet

Naming pressure is design pressure in disguise. Embrace it. Let the discomfort of a bad name push you toward better structure.

I keep a running list of naming patterns that have served me well. Not a dictionary, more like a field guide. Verbs for functions, nouns for data, adjectives for booleans. Simple patterns, but they eliminate an entire category of decision fatigue.

The next time you reach for temp or data or result, pause. That moment of friction is an opportunity. The name you choose will be read a hundred times. Spend the twenty minutes. It's the highest-leverage work you'll do all day.
