The Quiet Cost of Premature Abstraction

Every shared module starts with good intentions. But abstraction has a carrying cost, and most teams pay it without realizing.

There is a moment in every codebase where someone says, "We use this pattern in three places, we should extract it." The impulse is reasonable. Duplication feels wrong. DRY is one of the first principles we learn. The pull request gets approved quickly because the diff looks clean.

But six months later, that extracted module is the thing nobody wants to touch. It has grown conditional branches for each caller. Its interface is a compromise between three different needs. It sits in a shared/ directory that has become a graveyard of good intentions.

This is the quiet cost of premature abstraction. Not that the code is bad, but that it freezes the wrong decision in place and makes future change expensive.

Duplication is cheaper than the wrong abstraction

Sandy Metz put this sharply in a talk that has aged remarkably well: "Duplication is far cheaper than the wrong abstraction." It sounds contrarian until you have lived through a codebase where a single BaseService class tries to serve twelve different API endpoints with a sprawl of configuration options.

The issue is not abstraction itself. Abstraction is how we manage complexity. The issue is timing. When you abstract after seeing two examples, you are guessing at the shape of future variation. When you abstract after seeing five or six, you are responding to evidence.

The rule of three is a minimum, not a target. Three occurrences tell you a pattern might exist. They do not tell you what the right boundary is. Consider waiting longer, especially when:

  • The callers are in different domains with different change cadences
  • The "shared" logic contains business rules that may diverge
  • You cannot clearly name the abstraction without using the word "common" or "shared"

How to recognize premature abstraction

Most premature abstractions do not announce themselves. They feel productive at the time. But there are patterns that show up reliably:

  1. Boolean parameters controlling behavior. When a function takes isAdmin or legacy flags to branch internally, the abstraction is serving multiple masters. Each flag is a sign that the callers have different needs the interface is papering over.
  2. The configuration object grows. You start with two options. Then someone adds a third for their use case. Then a callback hook. The configuration object becomes the real API, and it is harder to understand than the duplicated code would have been.
  3. Changes require updating all callers. If modifying the shared module means touching every file that imports it, the coupling has not been reduced — it has been hidden. You have a single point of change that triggers a cascade.

A concrete example

Consider a notification system. You have email notifications and in-app notifications. Both need to format a message, resolve a recipient, and dispatch. The obvious move is to create a NotificationService base class.

notification-service.ts 
abstract class NotificationService {
  abstract send(recipient: User, message: string): Promise<void>;

  async notify(event: AppEvent): Promise<void> {
    const recipient = await this.resolveRecipient(event);
    const message = this.formatMessage(event);

    // Six months later, this grows:
    if (this.shouldThrottle(recipient)) return;
    if (this.isQuietHours(recipient)) {
      await this.queue(recipient, message);
      return;
    }
    if (event.priority === 'low' && this instanceof EmailNotification) {
      await this.batch(recipient, message);
      return;
    }

    await this.send(recipient, message);
  }
}

The base class started clean. But email and in-app notifications have fundamentally different constraints. Emails can be batched and throttled. In-app notifications are instant but need read-tracking. Push notifications have payload size limits. The base class becomes a negotiation between all of them.

Two separate implementations with a small amount of duplicated formatting logic would have been simpler to maintain, test, and reason about.

What to do instead

The alternative to premature abstraction is not permanent duplication. It is patient observation. Let the duplicated code live long enough to reveal its real shape before you extract it.

  • Copy-paste freely in the early stages. When you are still learning what the code needs to do, duplication gives each call site the freedom to evolve independently. This is not laziness — it is keeping your options open.
  • Extract data, not behavior. Shared types, constants, and configuration are usually safe to extract early. Shared behavior is where premature abstraction causes the most damage.
  • Use composition over inheritance. When you do extract, prefer small functions that callers compose rather than base classes that callers extend. Composition makes it cheap to stop using a shared piece. Inheritance makes it expensive.
  • Name the abstraction precisely. If you cannot name it without words like "base," "common," "shared," or "utils," you probably do not understand the boundary yet. A good abstraction has a name that describes what it does, not where it lives.

The cultural pressure to abstract

There is a reason premature abstraction is so common. Code review culture rewards it. A reviewer who sees the same ten lines in two files will almost always suggest extracting it. The comment feels helpful. The resulting PR looks clean. Nobody flags the carrying cost because it has not arrived yet.

This creates a ratchet effect. It is always socially easy to propose an abstraction and socially hard to propose removing one. Deleting a shared module feels reckless even when the module is making everything worse. The team has to agree that the abstraction was a mistake, and that conversation is uncomfortable.

The best engineering cultures I have worked in treat abstractions as experiments, not commitments. They make it normal to say: "This shared module served us for a while, but our needs have diverged. Let's inline it back into the callers and see if something better emerges."

A checklist before you extract

Before moving duplicated code into a shared module, run through these questions:

  1. Can you name the abstraction with a specific noun, not a generic one?
  2. Do all callers use the same interface without flags or conditional options?
  3. Will the callers change at the same time, for the same reasons?
  4. If one caller needs to diverge, can it stop using the shared module without a large refactor?
  5. Have you seen at least three to five instances of the pattern in production code?

If you answer "no" to more than one, the abstraction is probably premature.

When abstraction is right

None of this is an argument against abstraction. It is an argument for well-timed abstraction. The best shared modules I have seen share a few traits:

  • They were extracted after the team had lived with duplication long enough to see the stable core
  • They have a clear, specific name — not utils or helpers but RateLimiter or MarkdownParser
  • Their interface is small and their implementation is allowed to be complex
  • They can be deleted without rewriting the callers — just inlined

The right abstraction does not just remove duplication. It reveals a concept that was implicit in the codebase and gives it a name. That is a fundamentally different act from noticing two similar-looking code blocks and merging them.

Further reading and references

Sandi Metz — "The Wrong Abstraction" (2016). The blog post that crystallized this idea for many developers. Metz argues that existing abstractions should be re-evaluated when new requirements arrive, rather than extended with more conditional logic.

Dan Abramov — "Goodbye, Clean Code" (2020). A personal reflection on removing a "clean" abstraction that was making the code harder to change. Abramov connects premature abstraction to the broader problem of optimizing for the wrong metric.

John Ousterhout — A Philosophy of Software Design (2018). Ousterhout's concept of "deep modules" provides a useful frame: good abstractions have simple interfaces and complex implementations. Premature abstractions tend to be the opposite — complex interfaces hiding simple logic.

The next time you see duplication and feel the pull to extract, pause. Ask whether you are responding to the code's actual needs or to an aesthetic preference. The answer matters, because the wrong abstraction is harder to undo than the duplication it replaced.

Let the code be messy a little longer. The right shape will emerge.
