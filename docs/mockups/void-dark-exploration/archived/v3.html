The Case Against Premature Abstraction

Every layer of abstraction you add before you need it is a bet against your future self. Most of the time, that bet loses.

Three years ago, I joined a team that had spent six months building a "flexible" configuration system. It could handle any data shape, any validation rule, any transformation pipeline. It was, by every technical measure, an impressive piece of engineering.

There was just one problem: nobody could figure out how to add a new config field. What should have been a five-minute change required modifying seven files across three packages, updating two schema definitions, and running a code generation step that took forty seconds and produced errors nobody understood.

They had abstracted too early, too aggressively, and for requirements that never materialized. The system was designed to handle twelve different config formats. In production, they used one.

The Abstraction Instinct

Programmers are pattern-matchers by nature. We see two pieces of code that look similar, and something deep in our brains screams "don't repeat yourself." We reach for abstraction the way a carpenter reaches for a hammer. It feels productive. It feels right.

But the DRY principle, taken to its extreme, produces code that is worse than the duplication it was trying to eliminate. The problem is not repetition itself. The problem is coupling things that change for different reasons.

Consider this: you have two API endpoints that both validate an email address. Your instinct says to extract a validateEmail() function. That's fine. Email validation genuinely is one concept with one reason to change.

Now consider: you have two API endpoints that both return a user object with the same five fields. Your instinct says to extract a formatUserResponse() function. That's where things go wrong. Those two endpoints serve different consumers with different needs. When one consumer needs a sixth field, you're adding if branches to shared code.

Three Rules I Follow Now

After years of writing over-abstracted code and then suffering through the consequences, I've adopted three rules that have dramatically improved the systems I build.

1. Wait for the third occurrence

Two instances of similar code is a coincidence. Three is a pattern. I don't extract shared logic until I've seen the same structure appear three times with genuinely identical reasons to change. This is sometimes called the Rule of Three, and it remains one of the most underused guidelines in software development.

2. Prefer duplication over the wrong abstraction

Sandi Metz wrote about this in her excellent article The Wrong Abstraction, and I think about it weekly. A little copy-paste never killed anyone. A bad abstraction that six teams depend on can paralyze an entire organization.

3. Make the abstraction easy to delete

When I do create an abstraction, I design it to be removable. No deep inheritance hierarchies. No framework-level conventions that require you to restructure your entire application if the abstraction turns out to be wrong. If you can't inline the abstraction back into its call sites in under an hour, it's too coupled.

A Real-World Example

Let me show you what premature abstraction looks like in practice. Here's a data fetching layer I inherited on a recent project:

// The "flexible" data layer (actual production code, simplified)
class DataProvider<T, R extends Record<string, unknown>> {
  private transformer: DataTransformer<T, R>;
  private validator: SchemaValidator<R>;
  private cache: CacheStrategy<R>;
  private retryPolicy: RetryPolicy;

  constructor(config: DataProviderConfig<T, R>) {
    this.transformer = config.transformer ?? new IdentityTransformer();
    this.validator = config.validator ?? new NoopValidator();
    this.cache = config.cache ?? new NoCache();
    this.retryPolicy = config.retryPolicy ?? defaultRetryPolicy();
  }

  async fetch(params: FetchParams): Promise<R> {
    const cached = await this.cache.get(params);
    if (cached) return cached;

    const raw = await this.retryPolicy.execute(() =>
      this.fetchRaw(params)
    );
    const transformed = this.transformer.transform(raw);
    const validated = this.validator.validate(transformed);

    await this.cache.set(params, validated);
    return validated;
  }
}

Seven classes. Four generic type parameters. A plugin architecture with three extension points. And every single usage in the codebase passed the default values for transformer, validator, and cache. Here's what actually replaced it:

// What we actually needed
async function fetchUsers(): Promise<User[]> {
  const response = await fetch('/api/users');
  return response.json();
}

async function fetchPosts(authorId: string): Promise<Post[]> {
  const response = await fetch(`/api/posts?author=${authorId}`);
  return response.json();
}

Two plain functions. No generics. No plugins. No configuration objects. When we eventually needed caching for one of them, we added it to that one function. The other function never needed it.

The irony of premature abstraction: it's almost always motivated by a desire to make future changes easier. But the abstraction itself becomes the thing that makes future changes hard.

Signs you've over-abstracted:

  • New team members take days to understand the pattern
  • Simple changes require modifying multiple files
  • You have "Noop" or "Identity" implementations of your interfaces
  • The abstraction has more configuration options than call sites

When Abstraction Is Worth It

I'm not arguing against abstraction. Abstraction is one of the most powerful tools in programming. I'm arguing against doing it before you have evidence that it's the right abstraction.

Good abstractions share a few properties:

  1. They emerge from real usage. You don't design them up front. You notice them after writing concrete code three or four times.
  2. They have a narrow, stable interface. If your abstraction's interface changes every time a new consumer adopts it, it's not abstracting the right thing.
  3. They reduce cognitive load. After the abstraction, developers think about fewer concepts to accomplish the same task. If your abstraction introduces new concepts (strategies, providers, factories, registries), it needs to eliminate more concepts than it introduces.
  4. They make deletion easy. The best abstractions are the ones you can replace with a direct implementation in thirty minutes if they turn out to be wrong.

The Cost Nobody Talks About

There's a hidden cost to premature abstraction that goes beyond code complexity. It's the opportunity cost of understanding.

When you abstract something, you're making a claim: "I understand this domain well enough to identify its stable boundaries." Early in a project, that claim is almost always wrong. You haven't lived with the code long enough. You haven't seen how requirements actually evolve. You're guessing.

And here's the thing about wrong abstractions: they're harder to fix than no abstraction at all. With duplicated code, each copy is independent. You can change one without worrying about the others. With a shared abstraction, every change is a negotiation between all its consumers.

A Practical Checklist

Before you extract a new abstraction, run through this list:

  • Have you seen this pattern at least three times in real code?
  • Do all instances change for the same reason?
  • Can you name the abstraction with a domain concept, not a technical pattern? (EmailValidator, not StringProcessor)
  • Will the abstraction have fewer than three configuration options?
  • Can you inline it back into call sites in under an hour if it turns out to be wrong?

If the answer to any of these is no, wait. Write the concrete code. Ship it. Live with it. The right abstraction will reveal itself when you're ready.

Aside: The Gang of Four got this backwards

The original Design Patterns book presented patterns as things you plan for up front. In practice, patterns should be discovered, not applied. You don't start a project by deciding "I'll use the Strategy pattern here." You start by writing concrete code, and if you later find three algorithms that share an interface, then you have a Strategy.

This is not a criticism of the patterns themselves. They remain useful as a shared vocabulary. The mistake is treating them as a design methodology rather than a recognition tool.

Further reading on this topic

These are the articles and talks that shaped my thinking:

  • The Wrong Abstraction by Sandi Metz
  • Simple Made Easy by Rich Hickey
  • The Law of Leaky Abstractions by Joel Spolsky

Each one is worth revisiting every couple of years. You'll read them differently with more experience.

The best engineers I've worked with share a common trait: they're comfortable with duplication. They don't reach for abstraction as a reflex. They wait. They watch. They let the code tell them where the real boundaries are.

Premature abstraction feels like progress. But progress without direction is just motion. Write the simple thing first. You can always make it more abstract later. You can rarely make it more simple.
